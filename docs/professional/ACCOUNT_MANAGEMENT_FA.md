# مدیریت پرونده، اشتراک و حساب Pro

این بسته روی main با commit `a920f7884646861020fadc5b0d38ce87d72c66f8` (مرج PR شماره ۱۵) ساخته شده است. موتور تغذیه، منوها، ماکروها، PlanPreview و قالب PDF تغییر نکرده‌اند.

## قابلیت‌های این نسخه

- منوی انتخاب اختصاصی در فرم Pro، انتخاب فضای کاری، تاریخ تولد شمسی Pro و کنترل‌های مدیریت اشتراک ادمین؛ انتخاب با صفحه‌کلید و ظاهر روشن/تاریک.
- اصلاح فضای آیکن جست‌وجو و متن ورودی. پوسته اصلی Pro حفظ شده است.
- بخش «اشتراک و ظرفیت»: اعتبار، ظرفیت، تاریخچه تغییرات مجوز و درخواست تمدید. درخواست تمدید برای ادمین ثبت می‌شود؛ پرداخت، تمدید خودکار یا ارسال پیامک انجام نمی‌دهد. سابقه این بخش، سابقه مجوز Pro است؛ پرداخت‌های B2C به‌عنوان پرداخت Pro نمایش داده نمی‌شوند.
- بایگانی و بازگرداندن پرونده بدون حذف اطلاعات یا تغییر برنامه‌های قبلی. پرونده بایگانی‌شده فقط خواندنی است؛ خروجی PDFهای قبلی در دسترس است. بایگانی ظرفیت مصرف‌شده را کم نمی‌کند.
- هشدار شماره تکراری پیش از ساخت پرونده، شامل ارقام فارسی/عربی و قالب 09/+98. تصمیم نهایی با کاربر است؛ شماره مشترک خانواده ممنوع نشده است. اطلاعات کلینیک دیگر در جست‌وجوی مشابه افشا نمی‌شود.
- ادمین: ساخت حساب Pro با شماره تماس یا فعال‌سازی حساب تأییدشده با UUID، مدیریت اعتبار/ظرفیت/تعلیق، مشاهده درخواست‌های تمدید و پایان بررسی آن‌ها. ظاهر ادمین با پوسته Pro هماهنگ شده است.
- ساخت حساب از سمت سرور انجام می‌شود. شماره از طرف ادمین تأیید نمی‌شود؛ صاحب حساب هنگام ورود باید OTP را از مسیر موجود تأیید کند. عضویت و اعتبار آماده‌اند ولی دسترسی شماره تأییدنشده بسته است.

خرید خودکار Pro، دعوت همکار، تعیین دسترسی همکار و اتصال بیمار به B2C در این بسته نیستند.

## ۱. اعمال پچ روی سیستم

ZIP را بیرون پوشه پروژه استخراج کنید. فایل‌های `behtan-pro-account-management.patch` و `CHANGED_FILES.txt` را کنار package.json در `E:\Behtan-Final` کپی کنید. فایل‌های changed-files صرفاً برای مرور کدند؛ آن‌ها را هم‌زمان دستی جایگزین نکنید.

```powershell
cd E:\Behtan-Final
git status
git switch main
git pull --ff-only origin main
git switch -c feature/pro-account-management
git apply --check behtan-pro-account-management.patch
```

اگر تغییر شخصی commit نشده دارید، پیش از سوییچ آن را جدا حفظ کنید. اگر check خطا داد، ادامه ندهید و خروجی را بفرستید. سپس:

```powershell
git apply behtan-pro-account-management.patch
npm run test:pro
npm run test:admin
npm run test:onboarding
npm run test:age
npm run build
npm run build:admin
npm run build:pro
```

وابستگی جدید نداریم. اگر Playwright قبلاً نصب است، تست‌های مرورگر:

```powershell
npm run test:pro:browser
npm run test:pro:admin:browser
```

این تست‌ها از داده مصنوعی و اتصال کنترل‌شده استفاده می‌کنند. GitHub Actions نیز آن‌ها را اجرا می‌کند.

## ۲. Migration جدید — فقط ۰۲۷

پیش از انتشار کد جدید، در SQL Editor همان Supabase فعلی به‌تن، وجود Migration را بررسی کنید:

```sql
select to_regclass('public.pro_case_archive_events') as archive_events;
```

اگر null است، پس از بکاپ معمول پروژه، کل محتوای فایل زیر را یکجا اجرا کنید:

`supabase/migrations/20261021_027_pro_account_management.sql`

کپی همان فایل در پوشه migrations این ZIP هم وجود دارد. این Migration ساختار را افزایشی تغییر می‌دهد؛ داده‌ای حذف نمی‌کند. Migrationهای ۰۲۵ و ۰۲۶ را دوباره اجرا نکنید. اگر archive_events از قبل موجود است، Migration را تکرار نکنید؛ ابتدا وضعیت نصب قبلی را بررسی کنید.

پس از اجرا:

```sql
select
  to_regclass('public.pro_case_archive_events') as archive_events,
  to_regclass('public.pro_renewal_requests') as renewal_requests;
```

هر دو باید نام جدول را نشان دهند. این Migration پاسخ بررسی سلامت سرویس را به operations-v2 ارتقا می‌دهد؛ تا انتشار سرور جدید ممکن است بررسی فنی نسخه قدیم پیام ناهماهنگی بدهد.

## ۳. تنظیم سرور ادمین در Vercel

فقط پروژه **behtan-admin** → Settings → Environment Variables → Production:

```text
PRO_ADMIN_ACCOUNTS_ENABLED=true
SUPABASE_SERVICE_ROLE_KEY=<کلید service_role همان Supabase به‌تن>
```

متغیرهای VITE_SUPABASE_URL و VITE_SUPABASE_ANON_KEY همین پروژه نیز باید مثل قبل مربوط به همان Supabase باشند. کلید service_role فعلی پروژه behtan-pro را برای تابع سروری ادمین هم در تنظیمات Vercel ثبت کنید. نام کلید مدیریتی نباید VITE_ داشته باشد و مقدار آن نباید در فایل‌های Client، git یا چت قرار گیرد.

تنظیم‌های فعلی پروژه behtan-pro را حفظ کنید؛ این قابلیت نیازمند تغییر در send-sms، OTP یا پرداخت B2C نیست. برای Preview نیز اگر می‌خواهید ساخت حساب را تست کنید، envهای مناسب همان محیط را تنظیم کنید؛ داده مصنوعی به کار ببرید.

## ۵. تست دستی کوتاه

- Pro: انتخاب فضای کاری، تاریخ تولد و سایر گزینه‌ها را روی موبایل و دسکتاپ باز کنید؛ متن جست‌وجو زیر آیکن نباشد.
- Pro: «اشتراک و ظرفیت» را باز و یک درخواست تمدید ثبت کنید. درخواست تکراریِ باز نباید ساخته شود.
- Admin → «مدیریت Pro»: درخواست را ببینید؛ تغییر اعتبار/ظرفیت را در مدیریت فضای کاری ثبت کنید و پس از رسیدگی، «پایان بررسی درخواست» را بزنید. پایان بررسی به‌تنهایی اعتبار را تغییر نمی‌دهد.
- Pro: یک پرونده تست را بایگانی، از فهرست بایگانی باز، PDF قبلی را مشاهده و سپس پرونده را بازگردانی کنید.
- Pro: با شماره پرونده موجود، ثبت پرونده جدید را امتحان کنید؛ هشدار و تصمیم صریح لازم است.
- Admin → «مدیریت Pro» → «ساخت حساب Pro»: شماره‌ای تحت کنترل خودتان، نام پنل، اعتبار، ظرفیت و دلیل را وارد کنید. حساب جدید تا قبل از ورود OTP با برچسب انتظار تأیید شماره نمایش داده می‌شود.
- با همان شماره و OTP وارد pro.behtan.fit شوید؛ فضای کاری آماده باید در دسترس باشد. اگر شماره قبلاً حساب به‌تن دارد، همان حساب استفاده می‌شود. اگر پنل فعال به نام آن وجود دارد، ساخت پنل تکراری رد می‌شود.

ساخت Auth account و ساخت فضای کاری دو عملیات مجزا هستند. اگر ارتباط بین آن‌ها قطع شود، retry همان شماره و کلید درخواست حساب را پیدا و عملیات را ادامه می‌دهد؛ حساب ایجادشده را خودکار حذف نمی‌کنیم.

## فایل‌های داده و امنیت

Migration 027 دو جدول جدید با RLS و بدون دسترسی مستقیم Client ایجاد می‌کند: pro_case_archive_events (تاریخچه تغییرناپذیر بایگانی) و pro_renewal_requests. فیلدهای archived_at و archive_revision به پرونده افزوده می‌شوند؛ نسخه ورودی و برنامه تغذیه دست‌نخورده می‌مانند. ساخت برنامه جدید برای پرونده بایگانی‌شده در API و هنگام ثبت در دیتابیس متوقف می‌شود.

API جدید /api/pro-account ورود واقعی و نقش ادمین را سمت سرور بررسی می‌کند. RPCهای پیدا کردن شماره و آماده‌سازی حساب فقط برای service_role مجازند و خودشان نیز نقش ادمین تأییدشده را بررسی می‌کنند. هیچ نقش ادمینی به حساب جدید اعطا نمی‌شود.
