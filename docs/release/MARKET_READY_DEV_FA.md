# بستهٔ توسعه و بازبینی به‌تن

مبنا: `main@1f2bc04` · تاریخ: ۲۴ اکتبر ۲۰۲۶

این نسخه برای تست محلی است. هیچ push، Merge، deploy، تغییر تنظیمات سرویس یا اجرای Migration روی دیتابیس اصلی انجام نشده است. دسترسی اتصال PostgreSQL اصلی در این محیط موجود نبود؛ **بکاپ واقعی تولید نشده است**. اسکریپت بکاپ آماده شده، اما بکاپ باید توسط مالک دسترسی اجرا و بازیابی آن بررسی شود.

## ترتیب درست

۱. بکاپ مستقل از دیتابیس اصلی؛ ۲. بررسی بازیابی در دیتابیس دورریختنی؛ ۳. اعمال پچ روی شاخهٔ محلی؛ ۴. تست با Supabase محلی/محیط جدا؛ ۵. اصلاح‌های بعدی. فعلاً مرحلهٔ انتشار نداریم.

## ۱. بکاپ پیش از هر تغییر production

کلاینت PostgreSQL هم‌نسخه یا جدیدتر از سرور لازم است: `pg_dump`, `pg_dumpall`, `pg_restore`, `psql`. URL اتصال را از بخش Connect همان پروژه بگیر. برای سرور ابری، گواهی معتبر SSL لازم است؛ `PGSSLROOTCERT` را به فایل گواهی دریافتی از Supabase اشاره بده. غیرفعال‌کردن بررسی گواهی توصیه نمی‌شود.

در PowerShell، مقدار محرمانه را بدون نوشتن در تاریخچه وارد کن:

مسیر `E:\Behtan-Final` و پوشهٔ Downloads در مثال‌ها را مطابق سیستم خودت عوض کن.

```powershell
cd E:\Behtan-Final
$package = "$env:USERPROFILE\Downloads\behtan-market-ready-dev"
$secret = Read-Host "PostgreSQL connection URL" -AsSecureString
$env:BEHTAN_DATABASE_URL = [Net.NetworkCredential]::new('', $secret).Password
$env:BEHTAN_BACKUP_DIR = "E:\Behtan-Backups"
node "$package\backup-full.mjs"
Remove-Item Env:BEHTAN_DATABASE_URL
```

این دستور نسخهٔ داخل بستهٔ استخراج‌شده را اجرا می‌کند؛ مسیر `$package` را مطابق پوشهٔ خودت تنظیم کن. اجرای بکاپ فقط خواندنی است و به اعمال پچ یا اجرای Migration نیاز ندارد. نسخهٔ همین ابزار در پچ هم موجود است.

خروجی: `database.dump`، `roles.sql` بدون رمز نقش‌ها، فهرست آرشیو و checksum. آرشیو شامل داده و ساختار schemaهای قابل دسترسی، از جمله Auth و متادیتای Storage است. اگر دسترسی کافی نباشد، عملیات ناموفق اعلام می‌شود؛ خروجی ناقص را بکاپ کامل حساب نکن.

بکاپ دیتابیس، فایل‌های واقعی Storage، کلیدها، Secretهای توابع، تنظیمات Auth و تنظیمات Vercel را شامل نمی‌شود. این موارد جداگانه و در محل امن نگهداری شوند. بکاپ را در GitHub یا چت بارگذاری نکن.

برای تمرین بازیابی، فقط یک دیتابیس خالی و جدا به نام `behtan_restore_verification` با نقش‌ها/افزونه‌های لازم بساز. هرگز URL اصلی را به دستور بازیابی نده:

```powershell
$secret = Read-Host "Disposable restore database URL" -AsSecureString
$env:BEHTAN_RESTORE_URL = [Net.NetworkCredential]::new('', $secret).Password
node "$package\verify-full-backup.mjs" "E:\Behtan-Backups\BACKUP_FOLDER"
Remove-Item Env:BEHTAN_RESTORE_URL
```

بازیابی روی دیتابیس غیرخالی یا نام دیگر رد می‌شود. موفقیت restore به‌تنهایی تطبیق نهایی نیست؛ تعداد دقیق رکوردهای مهم در مبدا و مقصد، نقش‌ها، RLS و رابطه‌ها را بررسی کن. manifest تا تأیید دستی `restore_verified=false` می‌ماند. بعضی schemaهای مدیریت‌شدهٔ Supabase نیازمند نقش‌ها/افزونه‌های همان محیط‌اند؛ خطای آن‌ها نباید نادیده گرفته شود.

## ۲. اعمال پچ روی شاخهٔ محلی

ZIP را بیرون پروژه استخراج کن؛ مسیر فایل patch را در دستور قرار بده. ابتدا `git status --short` باید خالی باشد؛ تغییرات ذخیره‌نشده را reset یا پاک نکن.

```powershell
cd E:\Behtan-Final
git status --short
git switch main
git pull --ff-only
git switch -c feature/market-ready-local
$patch = "$env:USERPROFILE\Downloads\behtan-market-ready-v2\behtan-market-ready-v2.patch"
git apply --check $patch
git apply $patch
npm ci
```

اگر `--check` خطا داد، ادامه نده و از `--reject` استفاده نکن. پچ برای مبنای بالا ساخته شده است. فعلاً دستور push یا Merge اجرا نکن.

## ۳. محیط محلی جدا از دیتابیس اصلی

Docker Desktop و Supabase CLI لازم‌اند. از CLI سازگار با `supabase/config.toml` استفاده کن.

```powershell
npm run dev:prepare
supabase start --workdir .local-supabase
supabase status --workdir .local-supabase
```

`dev:prepare` فقط فایل تولید می‌کند؛ هیچ اتصال دیتابیس، reset یا deploy ندارد. schema، seed و Migrationها را در یک baseline محلی جمع می‌کند. `.local-supabase/` از Git خارج است. تمام baseline تولیدشده در PGlite اجرا و بررسی شده است؛ Docker/Supabase محلی در محیط ساخت این بسته اجرا نشده‌اند، بنابراین راه‌اندازی واقعی آن هنوز یک بررسی لازم روی سیستم شماست.

مقادیر خروجی status را در **`.env.local`** پروژه وارد کن. هیچ مقداری از پروژهٔ اصلی استفاده نکن:

```dotenv
VITE_SUPABASE_URL=http://127.0.0.1:54321
VITE_SUPABASE_ANON_KEY=LOCAL_ANON_KEY_FROM_STATUS
VITE_TURNSTILE_SITE_KEY=1x00000000000000000000AA
SUPABASE_SERVICE_ROLE_KEY=LOCAL_SERVICE_ROLE_KEY_FROM_STATUS
MEMBER_RELEASE_ENABLED=true
VITE_PRO_SANDBOX_ENABLED=true
```

شمارهٔ ورود محلی: **۰۹۱۱۱۱۱۱۱۱۱** · کد: **۱۲۳۴۵۶**. این تنظیم فقط در config تولیدشدهٔ محلی است؛ به config یا Auth production منتقلش نکن. ورود اصلی همچنان Supabase Phone OTP و Turnstile است و هیچ adapter دورزننده‌ای اضافه نشده است.

برای توابع محلی:

```powershell
Copy-Item .local-supabase\functions.env.example .local-supabase\functions.env
supabase functions serve --workdir .local-supabase --env-file .local-supabase/functions.env
```

فایل نمونه، callback بانکی را به `https://localhost.invalid` می‌فرستد تا اشتباهاً به سایت اصلی برنگردد. کلید مدل اختیاری است و فقط در فایل محلی خصوصی قرار می‌گیرد. بدون کلید، ثبت دستی و مسیر بدون عکس کار می‌کند؛ تحلیل واقعی عکس انجام نمی‌شود. Trial رایگان به درگاه نیاز ندارد. پرداخت بانکی انتها‌به‌انتها برای توسعه به callback HTTPS و تنظیمات sandbox معتبر نیاز دارد و در این بسته اجرا نشده است.

در ترمینال‌های جدا:

```powershell
npm run dev
npm run dev:admin
npm run dev:pro
```

برای ادمین، UUID حساب محلیِ واردشده را فقط در Studio محلی در جدول `admin_members` اضافه کن. این کار هیچ حساب production را تغییر نمی‌دهد. حساب تست عمومی را در سرویس اصلی نساز.

این نسخه با دیتابیس قدیمی بدون Migrationهای جدید کامل کار نمی‌کند؛ وصل‌کردن کد جدید به Supabase اصلی، تست محلیِ جدا محسوب نمی‌شود.

## تصمیم‌های مهم

- روز ورزشی در کاهش/افزایش وزن کالری پایه را عوض نمی‌کند؛ وعدهٔ اضافه از همان هدف سهم می‌گیرد. حفظ وزن طبق سیاست قبلی ۱۵۰ کالری اضافه دارد. تغییر علمی سیاست در این انتشار انجام نشده است.
- تمرین خودکار فعلی برای دامنهٔ عمومی ۱۸–۶۴ سال، ۲ یا ۳ جلسهٔ غیرمتوالی و تجهیزات مشخص است. غربالگری درد/محدودیت/جراحی و محدودیت‌های موتور حفظ شده‌اند؛ مسیر متخصص/توان‌بخشی جعل نشده است. بررسی اولیهٔ صلاحیت تمرین قبل از خرید ترکیبی انجام می‌شود و فرم تمرین همچنان باید کامل شود.
- مابه‌تفاوت ارتقا، تفاضل **قیمت فعلی همان دوره در کاتالوگ** است، نه قیمت تاریخی پرداخت یا محاسبهٔ روزشمار. تاریخ پایان اشتراک تغذیه حفظ می‌شود. Trial تخفیف اعتباری ندارد و دورهٔ کامل می‌خرد. نیم‌تومان رو به بالا گرد می‌شود.
- نسخهٔ دوم: فقط تحلیل موفقِ ذخیره‌شده سهمیهٔ پنج‌روزه را مصرف می‌کند. خطا سهمیه را آزاد می‌کند؛ برای کنترل هزینه حداکثر پنج تلاش در روز و یک درخواست هم‌زمان پذیرفته می‌شود. نتیجهٔ ذخیره‌شده هنگام بازگشت به پروفایل قابل مشاهده است.
- کاهش وزن یا کالری، «امتیاز بهتر» معرفی نمی‌شود. جشن برای ثبت داده است. با تغییر وزن، غذاهای خورده‌شده از تاریخچه حذف یا بازنویسی نمی‌شوند و گیت ایمنی دوباره اعمال می‌شود.
- Trial Pro به زمان سه‌روزه محدود نیست؛ سقف سه پروندهٔ واقعی در مجموع دارد و بایگانی ظرفیت را آزاد نمی‌کند. مجوز زیرساختی محدودیت تاریخ دوردست دارد؛ تأیید تخصص حرفه‌ای صادر نمی‌شود.
- نبض بیزینس فعلاً از حساب تأییدشده شروع می‌شود؛ attribution تبلیغات، بازدید ناشناس، درآمد خالص پس از هزینه/بازپرداخت و تحلیل آزمایش A/B هنوز دادهٔ واقعی ندارند. تعداد assertion، محصول/بازار را اثبات نمی‌کند.

## تست‌ها و معیار پذیرش محلی

```powershell
npm run test:market
node scripts/local-bootstrap.test.mjs
npm run test:production
npm run test:onboarding:lifecycle
npm run test:nutrition
npm run test:training
npm run test:landing
npm run build
npm run build:admin
npm run build:pro
```

تست‌های SQL جدید قیمت جعلی، binding پروفایل/کاتالوگ، دورهٔ ۱۴روز، Trial یک‌بارمصرف، تسویهٔ تکراری، ارتقا و تاریخ پایان، ساخت Trial Pro و رد پروندهٔ چهارم، خرید Pro بدون اعطای B2C، مجوز ادمین، ویرایش منو و محدودیت محاسبه را بررسی می‌کنند. دیتابیس آزمون از داده‌های مصنوعی استفاده می‌کند.

Lint ماژول‌های جدید بدون خطاست. Lint سراسری هنوز ۳۲ خطای قبلی در renderer موج، PanelSelect و fixtureهای تست Pro دارد؛ فایل‌های دارای این خطاها در این پچ تغییر نکرده‌اند. کل مخزن از نظر lint سبز اعلام نمی‌شود. بررسی وابستگی‌های اجرایی با `npm audit --omit=dev` در زمان ساخت بسته، آسیب‌پذیری شناخته‌شده‌ای گزارش نکرد؛ این نتیجه جای ممیزی امنیتی یا تست سرویس زنده را نمی‌گیرد.

باید در مرورگر واقعی هم بررسی شود: شروع از کاربر تازه، ثبت وزن و تغییر هدف، حفظ غذای خورده‌شده، ارتقا، تمام هفته‌های تمرین، برگشت و شکست شبکه، اسکن و سهمیه، پروفایل، ادمین و عرض موبایل. Playwright و PostgreSQL بومی برای این شاخه در این محیط اجرا نشده‌اند. fixtureهای جغرافیای آنبوردینگ به رفتار جدید تطبیق یافته‌اند، اما نتیجهٔ مرورگر ادعا نشده است.

## گزارش عملکرد

گزارش GTmetrix پیوست‌شده برای قبل از این تغییرات: Performance ۸۲٪، Structure ۹۴٪، LCP=۱٫۹s، TBT=۱۴۷ms، CLS=۰، حجم ۱٫۰۵MB. تصویر لوگو حدود ۳۵۵KB و تصویر اینماد پاسخ ناقص داشت. لوگوی نمایشی جدید حدود ۵٫۲KB است و آیکون‌های مستقل تولید شده‌اند. HTML عمومی بدون انتظار برای اجرای React محتوا دارد؛ بخش‌های reveal در نبود JS پنهان نمی‌مانند. نتیجهٔ جدید GTmetrix/CWV واقعی هنوز اندازه‌گیری نشده و بهبود امتیاز یا رتبهٔ گوگل تضمین نمی‌شود.

## Migration و بازگشت

فایل‌های ۰۳۵ تا ۰۳۹ فقط در محیط محلی یا clone بررسی می‌شوند. فعلاً آن‌ها را در SQL Editor اصلی Run نکن و `supabase db push` اجرا نکن.

این تغییرها افزایشی‌اند، ولی Billing RPC و متن کاتالوگ را تغییر می‌دهند. بعداً انتشار نیازمند هماهنگی API عضو، Edge پرداخت، اسکن و سه build خواهد بود. rollback صرفاً برگرداندن فرانت کافی نیست؛ تا طراحی و تست rollback انتشار، اجازهٔ production نداریم. بکاپ قبل از تغییر، جای برنامهٔ rollback را نمی‌گیرد. در بازبینی محلی می‌توان شاخه را کنار گذاشت؛ هیچ جدول اصلی نباید حذف شود.
