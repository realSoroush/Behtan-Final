# نسخهٔ سوم توسعهٔ به‌تن — اصلاحات بازبینی Astra

این بسته جایگزین کامل پچ قبلی است؛ روی پچ قبلی اعمال نمی‌شود. مبنا همان Main با شناسهٔ `1f2bc049447d53589f1d2ebf2b818641d010ad4c` است. هیچ Push، Merge، Deploy یا تغییر دیتابیس اصلی از طرف سازنده انجام نشده است.

## اصلاحات تکمیلی بازبینی دوم

- ادامهٔ پرداخت سفارش معلقی که پروفایل، کاتالوگ یا ورودی تمرین آن با پیش‌بررسی تازه ناسازگار است رد می‌شود. برای سفارش ناسازگار، کاربر باید نتیجهٔ پرداخت قبلی را بررسی کند؛ سفارش بانکی قبلی بی‌صدا حذف یا با محتوای تازه بازنویسی نمی‌شود.
- اگر کاربر پس از شروع پرداخت مشخصاتش را تغییر داده باشد، پرداخت و اشتراک محفوظ می‌مانند. برنامهٔ ناسازگار فعال نمی‌شود؛ در تب تمرین، اطلاعات تازه بررسی و برنامه بدون خرید دوباره ساخته می‌شود. این مسیر جایگزینِ نمایش برنامهٔ قدیمی یا گم‌شدن پرداخت است.
- ذخیرهٔ دوبارهٔ تمرین با نسخهٔ پروفایل خوانده‌شده تطبیق اتمیک دارد. اعتبار برنامه با snapshot پروفایل، شامل روزهای دقیق هفته، بررسی می‌شود. تغییر پروفایل به‌صورت محافظه‌کارانه می‌تواند ساخت دوباره را لازم کند؛ فقط تغییر updated_at برنامه را نامعتبر نمی‌کند.
- ثبت غذای اضافی، شناسهٔ ثابت عملیات دارد. تا روشن‌شدن نتیجه، تلاش مجدد و تازه‌سازی همان تب شناسه را نگه می‌دارد. دیتابیس درج تکراری همان شناسه را نادیده می‌گیرد. بعد از موفقیت تأییدشده، ثبت عمدی غذای دیگری شناسهٔ تازه می‌گیرد. فقط digest و شناسه در sessionStorage نگهداری می‌شود، نه عکس، نام غذا یا وزن. بسته‌شدن کامل نشست مرورگر این ضمانت را حفظ نمی‌کند.
- مجوز UPDATE جدول نخوردن صریح شده؛ تست با نقش authenticated و بدون پیش‌فرض UPDATE اجرا می‌شود.
- خرید و مراحل مهم گزارش اپ از پروفایل، پیش‌بررسی و سفارش‌های سمت سرور استخراج می‌شوند. دیررسیدن یا حذف رویداد مرورگر باعث جاافتادن خرید نمی‌شود. نام و توضیح گزارش روشن می‌کند که این پوشش مراحل یک کوهورت است، نه قیف زمانی بازدید ناشناس. برای نرخ تبدیل تبلیغات همچنان دادهٔ جذب لازم است.

## اصلاحات حفظ‌شده از نسخهٔ قبلی

- وضعیت نخوردن وعده با تاریخ تطبیق داده می‌شود؛ نخوردن صبحانهٔ امروز، صبحانهٔ فردا را مخفی نمی‌کند. در دیتابیس، ثبت خورده‌شدن و نخوردن همدیگر را در یک تراکنش پاک می‌کنند. خطای دریافت وضعیت پنهان نمی‌شود و درخواست تکراری نخوردن مهار می‌شود.
- Edge تحلیل بدن، نتیجهٔ معتبر را پیش از ارسال پاسخ ذخیره می‌کند. بستن صفحه، قطع پاسخ یا تازه‌سازی باعث از دست رفتن گزارش ذخیره‌شده نمی‌شود. گزارش در پروفایل حتی در دورهٔ انتظار قابل مشاهده است. عکس در جدول یا Storage ذخیره نمی‌شود و نتیجهٔ جدید اسکن پروفایل وارد محاسبهٔ کالری نمی‌شود.
- فقط نتیجهٔ موفق سهمیهٔ پنج‌روزه را مصرف می‌کند. شکست سرویس آزاد می‌شود؛ برای کنترل هزینه حداکثر پنج تلاش در ۲۴ ساعت و یک درخواست هم‌زمان مجاز است. قفل درخواست قطع‌شده بعد از دو دقیقه منقضی می‌شود.
- پیش‌بررسی، پروفایل استفاده‌شده را با نسخهٔ فعلی دیتابیس در تراکنش مقایسه می‌کند؛ تغییر وزن، آلرژی یا اطلاعات دیگر قبل از ذخیرهٔ تأییدیه، آن را نامعتبر می‌کند. ایجاد سفارش هم نسخهٔ پروفایل و کاتالوگ را با قفل مناسب بررسی می‌کند.
- دامنهٔ Pro و پورت محلی ۵۱۷۵ برای پرداخت مجازند؛ مبدأهای دلخواه مجاز نشده‌اند. بازگشت پرداخت Pro تا تأیید واقعی، توکن بررسی را نگه می‌دارد؛ نتیجهٔ نامشخص به عنوان موفق نمایش داده نمی‌شود.
- تسویهٔ Sandbox در Pro فقط مسیر بانکی را آزمایش می‌کند و فضای کاری یا مجوز تجاری نمی‌سازد. Trial سه‌پرونده‌ای مسیر جداگانهٔ خود را دارد. برای جلوگیری از حذف قابلیتِ مدت پرداخت‌شده، تغییر نوع پلن Pro فعال نیاز به پشتیبانی دارد؛ تمدید همان پلن مجاز است. تغییر خودکار نوع پلن با زمان‌بندی یا اعتبار مالی در این نسخه اضافه نشده است.
- اطلاعات ضروری تمرین پیش از خرید ترکیبی و ارتقا دریافت می‌شود. موتور باید واقعاً برنامه بسازد؛ صرف واجدشرایط بودن پزشکی کافی نیست. سفارش به برنامهٔ تأییدشده وصل است و پس از تسویه، برنامه در همان تراکنش فعال می‌شود. تغییر ورودی‌های مرتبط در پروفایل، برنامهٔ قدیمی را نامعتبر می‌کند و کاربر باید دوباره بسازد. اطلاعات لازم یا پاسخ‌های ایمنی حدس زده نمی‌شوند.
- غذای اضافی به طور پیش‌فرض مستقل ذخیره می‌شود؛ چند غذای اضافه برای یک وعده ممکن است و وعدهٔ قبلی حفظ می‌شود. کاربر می‌تواند به‌جای آن، جایگزینیِ تأییدشده را انتخاب کند. غذای اضافه در کالری مصرف‌شدهٔ امروز حساب می‌شود و نام و وزن مواد و امکان بازگرداندن ثبت نمایش دارد.
- در ثبت دستی، شناسهٔ کاتالوگ و مبنای خام، خشک یا پخته تا ذخیرهٔ نهایی حفظ می‌شود. برچسب وزن در انتخاب ماده و نتیجه دیده می‌شود. ثبت دستی با تخمین عکس تفکیک می‌شود و غذای دلخواه وارد نسخهٔ غذایی روز بعد نمی‌شود. هیچ عدد ماکرو یا کالری مادهٔ استاندارد تغییر نکرده است.
- Trial پولی شمرده نمی‌شود. فعال‌سازی رایگان از خرید با مبلغ مثبت جداست. گزارش مراحل اپ از رکوردهای معتبر سمت سرور برای یک گروه کاربر ساخته می‌شود؛ پرداخت‌ها به تفکیک اپ/Pro، پلن و مدت هم گزارش می‌شوند. این آمار فقط کاربران واردشده را پوشش می‌دهد؛ ردیابی بازدید ناشناس، جذب تبلیغاتی و انتساب کانال بازاریابی همچنان وجود ندارد.
- آنبوردینگ Pro از استایل‌های خود Pro استفاده می‌کند. فرم تمرین مشترک است و رفتار ذخیرهٔ فرم تکمیل پروفایل با تغییر پروفایل هماهنگ شده است.
- تست‌های بازگشت خطا به مجموعهٔ `test:market` و CI اضافه شده‌اند.

## اعمال پچ روی لوکال

۱. فایل ZIP جدید را از حالت فشرده خارج کن. پچ قدیمی را اعمال نکن.

۲. در PowerShell داخل پروژه اجرا کن:

```powershell
cd E:\Behtan-Final
git status --short
```

اگر خروجی دارد، اول تغییرات خودت را نگه‌داری و مشخص کن؛ دستورهای بعد را روی تغییرات ثبت‌نشده اجرا نکن. از reset یا clean استفاده نکن.

۳. شاخهٔ محلی بساز و مسیر پچ استخراج‌شده را وارد کن:

```powershell
git switch -c feature/market-ready-v3-local
$patch = "$env:USERPROFILE\Downloads\behtan-market-ready-v3\behtan-market-ready-v3.patch"
git apply --check $patch
git apply $patch
npm ci
npm run test:market
npm run test:security:hardening
npm run build
```

اگر `git apply --check` خطا داد، ادامه نده و از `--reject` یا اجرای پچ قدیمی استفاده نکن. مبنای شاخه را با `git rev-parse HEAD` بررسی کن؛ پچ به‌صورت تمیز و بایت‌به‌بایت روی مبنای بالا آزموده شده است.

۴. برای اجرای اپ، دیتابیس محلی جدا لازم است. [مراحل ساخت محیط محلی](MARKET_READY_DEV_FA.md#۳-محیط-محلی-جدا-از-دیتابیس-اصلی) را اجرا کن: Docker Desktop، `npm run dev:prepare`، `supabase start --workdir .local-supabase`، تنظیم `.env.local` با کلیدهای محلی و اجرای توابع محلی. بعد `npm run dev`، `npm run dev:pro` و `npm run dev:admin` را در ترمینال‌های جدا اجرا کن.

کد جدید را برای تست به Supabase اصلی وصل نکن. Migrationهای اصلاح‌شدهٔ ۰۳۵ تا ۰۳۹ هنوز منتشر نشده‌اند و به همین دلیل در همین بسته اصلاح شده‌اند؛ این نسخه، migration ارتقا برای دیتابیسی که پچ قبلی روی آن اجرا شده باشد نیست. اگر قبلاً یک clone آزمایشی با نسخهٔ قبلی ساخته‌ای، یک محیط محلی جدا برای نسخهٔ سوم بساز.

## چک‌لیست بررسی دستی

- صبحانه را نخورده ثبت کن، فردا را باز کن؛ صبحانهٔ فردا باید نمایش داده شود. برگرد، خورده ثبت کن و سپس ثبت را بازگردان؛ بعد از رفرش وضعیت نباید متناقض باشد.
- تحلیل بدن موفق را ببین، بدون زدن ادامه ببند و دوباره باز کن؛ همان گزارش باید قابل مشاهده باشد. شکست مدل نباید محدودیت پنج‌روزه بسازد، هرچند محدودیت تلاش روزانه برقرار است.
- یک وعدهٔ معمول را خورده ثبت کن؛ سپس دو غذای دستی اضافی برای همان وعده اضافه کن. هر سه ثبت باید باقی بمانند و کالری مصرف‌شده شامل همه باشد. یکی از اضافه‌ها را بازگردان و رفرش کن.
- سویا یا جو خشک انتخاب کن؛ مبنای وزن باید روشن باشد. وزن را از ۱۲۵ به ۱۵۰ گرم تغییر بده و تناسب کالری را بررسی کن.
- برای پلن ترکیبی، تجهیزات ناکافی یا روزهای نامعتبر بده؛ پیش از سفارش باید خطا بگیری. سپس اطلاعات معتبر بده؛ بعد از تسویهٔ آزمایشی B2C برنامهٔ تأییدشده باید در تمرین دیده شود. تغییر وزن یا وضعیت پزشکی باید برنامهٔ قبلی را برای بازسازی علامت بزند.
- Trial رایگان را فعال کن؛ تعداد خرید پولی و درآمد نباید زیاد شود.
- در Pro، Trial سه پرونده دارد. پرداخت Sandbox نباید ظرفیت تجاری یا پنل جدید بدهد. آزمون واقعی بانکی/تجاری به محیط جدا و callback HTTPS معتبر نیاز دارد؛ به‌جای آن روی پروژهٔ اصلی آزمایش نکن.
- نمایش موبایل، کیبورد، دسترسی با Back، حالت تاریک، خروج وسط عملیات و خطاهای شبکه را در مرورگر واقعی بررسی کن.

## بک‌آپ و انتشار

بک‌آپ واقعی پروژهٔ اصلی در این مرحله گرفته نشده است. اتصال MCP به معنی داشتن آرشیو قابل بازیابی نیست. اسکریپت بک‌آپ جدید، شمار دقیق ردیف‌ها را در همان snapshot مورد استفادهٔ `pg_dump` ثبت می‌کند. اسکریپت بازیابی، checksum و شمار دقیق هر جدول را مقایسه می‌کند و دیگر مجوزها را با `--no-acl` حذف نمی‌کند؛ نقش‌های لازم باید قبلاً در مقصدِ کاملاً جدا آماده شده باشند. استفاده از دیتابیس اصلی به عنوان مقصد ممنوع است.

حتی پس از تطبیق شمار ردیف‌ها، آزمون نقش‌ها، مالکیت، Auth، دسترسی Storage و فایل‌های بیرون دیتابیس لازم است. `restore_verified` تا آن بررسی‌ها false می‌ماند. هیچ دستور انتشار یا اجرای migration اصلی در این مرحله توصیه نمی‌شود.

## حدود تأیید این نسخه

- تست‌های SQL در PGlite انجام شده‌اند؛ PostgreSQL بومی، Docker محلی و پرداخت واقعی در این محیط اجرا نشده‌اند.
- تست نصب تمیز پچ، بیلد اپ/ادمین/Pro، تست‌های موجود مرتبط و سناریوهای بازگشت خطا اجرا شده‌اند؛ گزارش دقیق در TEST_RESULTS.txt است.
- بازبینی بصری و Core Web Vitals واقعی سایت، آزمون بازیابی بک‌آپ اصلی و بررسی جامع همهٔ غذاهای ترکیبی ایرانی هنوز انجام نشده‌اند. برچسب مبنای وزن و حفظ آن اصلاح شده، اما این به معنی تأیید تغذیه‌ای تمام دستورهای ایرانی نیست.
- سؤال‌های ایمنی و سؤال‌های مؤثر در محاسبه حذف نشده‌اند. کوتاه‌سازی قبلیِ آنبوردینگ و انتقال شهر/استان حفظ شده‌اند؛ بازنویسی کامل آنبوردینگ جزو این پچ اصلاحی نیست.
